# 追上最新一句后的等待：本机延迟评估

2026-09-13。评估代码基线 `1bdf762`，MacBook Air M4 / 24 GB，App 1.1.0 build 7，Qwen3-ASR 0.6B MLX INT8、HY-MT1.5-1.8B Q8_0、Kokoro ONNX CPU 2 线程。此次分析既有 10 分钟实机记录和当前代码，没有重启正在运行的传译，也没有调整模型或生产参数。

## 结论

最值得优先验证的是 **缩短 TTS 第一段音频的生成时间，以及让本机直接播放 PCM**。固化规则也可以更精细，但不能把所有空档归因于翻译未固化。

指定视频前 10 分钟的 87 条朗读之间共有 86 个间隔，其中 23 个超过或等于 2 秒；**18 个长间隔在上一句结束前，下一句译文就已经完成**。这批数据说明，只加快翻译或者降低一个固化计时参数，覆盖不到大部分长空档。

## 记录给出的证据

输入来自 [原生长测记录](MACOS-PLAYBACK-LONG-TEST.md)，本次重新对齐原文版本、译文、语音标记和 AVPlayer 时间线。87 条音频均能按完整译文唯一匹配；监控记录出现 89 个原文版本，2 个句子被后续修订。这个修订计数不等同于 ASR 错误率，也不能说明其他句子都准确。

| 观察区间 | 中位数 | P90 | 解释 |
| --- | ---: | ---: | --- |
| 最终采用的原文版本首次出现在监控 → 译文出现 | 1.083 秒 | 1.644 秒 | 包含翻译排队和结果发布，非纯模型耗时 |
| 译文出现 → 音频语句标记发布 | 3.713 秒 | 5.937 秒 | 合并了放行、预合成、串行队列；旧记录不能精确拆开 |
| 音频标记发布 → 观察到可播放证据 | 4.976 秒 | 10.196 秒 | 包含前面音频排队，不能全部算作 HLS 缓冲 |
| 可播放证据 → 播放位置进入句首 | 0.433 秒 | 1.296 秒 | 包含自然停顿、句首余量和播放调度 |

“可播放证据”取满足原生安全跳转窗口条件和实际顺序播放到句首两者中的较早时刻。9 条顺序播放比满足跳转保护窗口更早，因此不能把安全跳转条件误当作普通播放的必要条件。监控/字幕采样约 0.53 秒，播放器约 0.1 秒；这些阶段数据不支持毫秒级精度，也不能直接相加各列中位数估算总延迟。

一个明确的长句例子：

| 长测经过时间 | 状态 |
| --- | --- |
| 172.284 秒 | 原文版本进入监控 |
| 174.394 秒 | 英文译文完成；TTS 已进入放行后的合成任务，之前队列为空 |
| 175.562 秒 | 上一句朗读结束 |
| 182.400 秒 | 下一句音频标记出现 |
| 185.488 秒 | 下一句进入原生安全跳转窗口 |
| 185.992 秒 | 播放位置进入下一句语音 |

这次空档为 **10.430 秒**：上一句结束后，约 **6.838 秒**仍处于音频生成/发布之前，再等 **3.088 秒**进入可播放窗口，最后约 **0.504 秒**到句首。该句英文 38 词、有效语音约 12 秒；等待期间 `synthesis_active=true`，译文出现时 `preparation_active=false`，表明已经进入放行后的合成分支。不能把这 6.838 秒解释成纯固化计时。

另一个例子先进入预合成，在第 566.909 秒已经有放行任务排队，但音频直到 571.759 秒才出现：预合成与固化已重叠，合成仍可能晚于放行完成。最长的 14.662 秒空档同时遇到原文修订、翻译、合成与播放准备；减少任意一层不等于能消除整段空档。

## 固化规则实际如何工作

[Mac 启动配置](../tools/macos_service.py#L77) 开启 `segment-final-redecode`，所以 [TTS 放行规则](../voxbridge/tts/jobs.py#L300) 按下列顺序生效：

| 原文状态 | 当前规则 | 可优化空间 |
| --- | --- | --- |
| 片段最终校验通过、已封口 | 译文就绪即可放行 | 已无额外固化计时 |
| 已被后续 token 确认 | 原文版本保持 3 秒 | 可试验有条件降至约 1 秒 |
| 最新一句，未被确认也未封口 | 等后续证据或片段最终校验 | 降低 4 秒宽限参数不解决这个分支 |
| 已有更新句子的其他未封口句 | 原文版本保持 3 秒 | 仍需检查修订与顺序风险 |

3 秒从原文版本登记时计时，**不是翻译完成后重新等待 3 秒**。翻译、预合成和固化已经部分并行。[译文完成处理](../voxbridge/cli/demo_streaming_ws.py#L7878) 会立即请求预合成；现有调度器也按事件及精确截止时间唤醒，没有固定数秒轮询等待。

使用实际 `RevisionStableTTSBuffer` 和可控时钟离线验证：原文在 0 秒登记、译文在 0.8 秒完成、8 秒封口。最新未确认句子的参数从 `3+4` 改成 `3+0`，甚至 `1+0`，都仍在 8 秒放行。已确认句子则可从 3 秒放行变成 1 秒。这个例子证明规则差异，不代表本次实测每句有 8 秒等待，也不代表听觉延迟必然改善 2 秒。

## 建议的优化顺序

### 1. 保留完整译文，优先缩短第一段 TTS 的交付

当前 [Kokoro 包装器](../voxbridge/tts/kokoro_onnx.py#L146) 调用 `model.create()`，整句 PCM 完成后，[HLS 工作线程](../voxbridge/tts/hls.py#L1428) 才交付音频。它的总吞吐可以追上讲者，但每次队列用尽后仍暴露整句合成时间。

建议在**完整译文确定后**按自然分句输出较小的音频块，首块以约 3–5 秒语音为试验目标，边播放边合成后续块；这是候选参数，不是本机已验证的性能承诺。文本语义和翻译上下文仍保持完整，音色及模型保持现有配置。同一句的内部块不能重复添加句末停顿，需要验证韵律、拼接及下一块是否能在前一块结束前准备好。

本机 `kokoro-onnx 0.5.0` 虽有 `create_stream()`，但内部仍按较大的音素批次生成，许多普通句子只占一批。**单纯把 `create()` 换名成 `create_stream()` 不足以解决首音延迟**；需要控制自然分句/音素块大小。这也与上游关于流式批次大小的[问题记录](https://github.com/thewh1teagle/kokoro-onnx/issues/130)一致，具体实现应以本机安装版本为准。

预合成继续使用精确原文版本、完整译文和方向校验。修订时丢弃未播的旧块，已播放内容保持不可撤回；停止和重启必须清空所属会话的任务。缩小合成块还有助于在块间终止过时预计算，避免旧长句占着单个合成线程。

### 2. 本机用原生 PCM 播放，局域网继续使用 HLS

本机 App 可以从服务获得获准播放的 PCM 块，通过 AVAudioEngine/AVAudioPlayerNode 顺序调度。HLS 继续服务局域网听众，两路复用同一份音频，避免重复合成。这样本机不必每次重新等待 AAC 片段发布和 AVPlayer 的实时播放窗口。

上述明确长空档中，音频标记到可安全播放约 3.1 秒；这是优化传输路径的证据，并非采用 PCM 后必然节省的秒数。PCM 仍需小缓冲防止欠载，并处理输出设备切换、取消、顺序和节奏。若还要求本机与手机同步听，则需要另设对齐策略，不能同时承诺最低本机延迟和严格同步。

### 3. 让固化策略感知真实的待播时间，优先放行已确认的内容

先把 App 的实际播放进度、正在读的句子、剩余可连续播放时长反馈给调度器。当前服务端 `translated_audio_backlog_ms` 含预估合成时长，已经编码但尚未被用户听到的部分又可能退出该统计，不能直接代表用户耳边剩余多少秒。

当真实待播时间只剩约 1–2 秒时，优先试验：对已确认且译文版本一致的完整短句，将 3 秒保护缩短为约 1 秒；积压较多时保留原策略。这只在固化规则晚于音频准备时有效。最新未确认尾句仍应依赖真实识别证据，不能为了填空强制把半句读出去。

再单独试验更早的可靠封口：在完整句法边界、识别稳定且 VAD 可信时，把静音阈值 0.8 秒降到 0.6 秒。这一改动本身只缩短符合条件处约 0.2 秒的阈值等待，不是几秒级收益保证。连续讲话时可评估更短的自然子句提交，不能按固定字数截断否定、专名、经文编号或中英混合词。已有 `PendingClausePolicy` 目前只有 off/shadow 接入，不能把开启 shadow 说成已经改变生产提交行为。

### 4. 预先翻译作为补充，按需评估 ASR 解码频率

对连续多次真实解码一致、语义完整的候选短句提前调用 HY-MT，并在正式提交时校验原文、版本、方向和完整提示词上下文；完全一致才复用，否则废弃。单个预计算任务、去抖、正式任务优先，可以限制额外 Metal 竞争；正在推理的无效任务也可能短暂阻塞正式翻译，需要测量。

本次正式原文到译文中位数约 1.1 秒，23 个长空档里只有 5 个还暴露了原文/翻译等待，因此预先翻译应排在前两项之后。它能重叠部分计算，不能代替最终正确性校验，也不能承诺每句少等 1.1 秒。

ASR 的 2 秒解码块可另做 1 秒对照，但更频繁的解码与 HY-MT 共用本机计算资源，不能假设延迟整体减半。Qwen [官方流式示例](https://github.com/QwenLM/Qwen3-ASR/blob/main/examples/example_qwen3_asr_vllm_streaming.py) 也使用 2 秒块和 5 个未固定 token；它是参考配置，并不是本机延迟最优的证明。应保留当前有效的最终重解码校验，实测识别一致性与热负载后再决定。

## 下一轮受控验证应补充什么

现有十分钟记录没有逐句固化/合成事件，无法精确统计“纯固化等待占比”。下一次受控测试需要以同一会话、原文版本和音频块 ID 串联：最后有效语音、原文提交/确认/封口、翻译排队与完成、合成开始与首块完成、获准播放、原生实际播放开始。把等待原因呈现为“原文待确认 / 正在翻译 / 正在合成 / 待播放”也能避免界面误导。

依次对照首块合成、PCM 播放、自适应固化，单独测量每项，最后再组合。继续使用同一视频前十分钟，保留源音频范围、模型及提示词一致。关注追上后的空档 P50/P90/最大值、译文就绪到首音、已播放后出现修订、断词/漏读/重复、停止重启及 CPU/Metal/热状态。不能通过长期增加播报落后量来美化连续性统计；实际源语音到听到译音的延迟也必须记录。
