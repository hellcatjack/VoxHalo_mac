## 基线中已确认的问题

### 1. 硬切后携带的前缀，可能一直等到下一次封口

重放 source order 4 的翻译仅用 344 毫秒，却在翻译完成后等了 **11.356 秒** 才获准发布。
放行前原生缓冲和 HLS pending 均为 0，已存在预合成音频；封口后，放行与首 PCM 提交发生在同一毫秒。
其他三个已准备音频、原生缓冲为空的案例，也分别等待约 10.857、10.632 和 8.556 秒。
这些空档不能归因于翻译模型慢或播放器缺少可播放窗口。

order 4 的直接原因是：前一个 12 秒硬切保留了一段前缀，最终重解码被 `live_hard_cut` 路径跳过。
下一窗口登记这段前缀，但后续 raw 解码没有再覆盖完整前缀，因而不能提供新的完整词序证据。
即使后续内容不断增长，确认仍停在 `content_agreement`，直到下一次硬切封口。
“ledger 里存在这段文本”不等于“新的真实解码确认了它”；不能把携带文本当作新解码票数。

### 2. 新修订吸收相邻旧行，旧行仍会再次发布

另一处实证发生在追踪经过约 135–142 秒：

| 时间 | 状态 |
| --- | --- |
| 134.960 秒 | 登记相邻的 row 28 和 row 29 |
| 137.078 秒 | row 28 的 revision 2 吸收 row 29；新源 token occurrence tuple 精确包含两行原有范围 |
| 随后 | row 29 仍保留 revision 1，确认从 1/1 降为 0/0；后续词数继续增长 |
| 141.145 秒 | 完成单元数回退，旧候选又被 backfill 保留 |
| 141.152 秒 | row 28 revision 2 首次发布 PCM，包含被吸收的内容 |
| 142.257 秒 | hard-cut seal 后，row 29 revision 1 又发布同一源范围的译音 |

这是**重叠内容的两次共享 PCM 发布**，不是单凭字幕相似度推断，也不是新的真实重复讲话。
它同时增加朗读量和顺序等待。build 41 的源句升级主要按候选下标配对，缺少多行被吸收时的原子范围移交。
本次没有物理扬声器录音，因此不把服务器发布记录描述成逐句听觉录音结果。

### 3. 确认等待后的集中放行，会形成播放积压

记录同时出现“播放器空、音频已准备但不能放行”和“随后连续放行、原生缓冲近 20 秒”。
解决前者时必须关注后者；额外攒播放缓冲只能改善连续性，可能进一步增加实际落后量。
某些修订在放行后仍等待 4–8 秒；现有追踪不足以把它拆成旧任务占用、Kokoro 推理或发布背压，不能全部计为纯合成时间。

## 基线后的推荐修复顺序及验收条件

1. **先修源句重分段的协调。** 按 occurrence 范围管理未发布源句所有权。更大修订吸收相邻行时，须在同一提交事务中更新范围、失效旧翻译和预合成、退休被吸收行；封口不得复活它们。已发布源范围不可撤回、不可被整句重新朗读。只有替代行确实保留全部源范围时才允许移交，不能通过删除旧行掩盖重复。
2. **再修硬切前后的证据衔接。** 保留待确认尾部的音频和证据来源，对仍缺证据的范围进行有界真实重解码，或在提交前把不完整短前缀保留在后续完整单元中。两条路径都须实测计算成本与韵律；不能用计时超时、低缓冲或 carried 文本代替源证据，也不能通过频繁硬切直接放行不完整语义。
3. **最后优化剩余合成和节奏。** 增加当前任务身份、撤销时刻、锁等待、首块完成与发布背压记录，再评估过时预合成占用。发布后的 PCM 不能因后续修订被跳过。中文保持整句自然朗读，继续限制在 1.2–1.5×。

缩短固定句间静音和把原生播放反馈用于后续语速决策，仅为辅助项。
峰值积压时已使用 1.5×，反馈不会重新加速既有 PCM；把每句额外 300 毫秒停顿减到 100 毫秒，对当时最多 6 个待消费末块的理论收益上界约 1.2 秒，不能解决 11 秒的确认等待。
这个上界也不是实测收益：尚未放行下一句时，省下的停顿可能被等待吸收。

后续代码必须用发生过的 raw/carry/单位合并顺序做回归，并验证：测试中每个已接受的源 occurrence 最终只被一次发布覆盖；真实重复讲话保留；否定、数字、专名和尾句无缺失；旧修订合成不能通过首 PCM 防线；停止、重启和封口不会恢复已被吸收的行。
再用同一固定音频区间做前后对照，同时统计确认等待、首次 PCM、原生积压和尾句排空。没有满足这些条件，不应宣称延迟已经修复。
源范围协调只负责此次重分段的完整性；队列饱和、ASR 漏识和翻译语义误差仍需独立验收，不能由此次回归推导全系统零遗漏。

## build 42：实现范围与安全边界

2026-10-04 开始落实前述前两项修复。此次实现协调源句范围与分段衔接，保留现有确认规则；没有替换大模型、改动提示词或调整朗读速度。Qwen3-ASR 0.6B MLX INT8、HY-MT1.5-1.8B Q8_0、Kokoro `zm_029` 与中文自动语速 **1.2–1.5×** 保持不变。

### 完整、未发布的相邻源行，按 token 范围原子合并

本阶段多行范围协调只在英语输入、原生 PCM 且朗读输出启用的路径中应用，重点验收英语 → 中文。其他输入语言与播放路径不因本次修改而自动获得同等验收结论。

更大的当前完整单元吸收旧行时，使用源 token occurrence ID 判断覆盖关系，不以相似文字、相同译文或候选下标判断重复。第一行保留自己的句子 ID 和发布顺序，登记新的 revision；后续被完整吸收的行进入明确的 `superseded` 终态，记录替代 owner 及其 revision。

合并必须同时满足以下条件：

- 涉及的旧行在活动源句顺序中连续，revision 与当前绑定一致，且尚未首次发布共享 PCM。
- 当前单元的 token 范围恰好等于全部旧范围按原顺序拼接的结果，每个 occurrence 都保留一次；不能只吸收部分旧行，不能夹带未登记的新词。
- 旧范围仍能映射到当前解码，当前完整单元之间不存在竞争的重叠范围。
- 不涉及已发布范围、部分覆盖记录或待发布补充句；移除子行后的整个已登记前缀仍与当前完整单元范围对应。

任何一项证据缺失或位置不一致，整组操作暂缓，不删除旧行。源 ledger、owner 新 revision、被吸收行退休、翻译请求有效性以及音频发布防线在同一个提交事务中更新，事务内部不等待异步任务。过时的翻译和预合成即使稍后完成，也不能越过当前 revision 的首 PCM 防线。

退休行从活动候选与字幕数组移除，避免完成单元数回退时被 backfill 重新加入。迟到 MT、旧 revision 注册、重新确认、封口、重试或结束强制排空都不能将其恢复为待播行。网页监控保留带 owner 信息的校订历史，活动行不再显示已吸收子行；无声字幕模式也取消其未显示页面，已经显示的字幕保留原阅读时长。以上展示处理不控制音频调度。

已发布 PCM 不撤回、不跳过，也不因 owner 后续修订而整句重播。owner 后续修订仍须保留已经接管的源范围；不能通过缩短 owner 或删除旧行掩盖尾部缺失。新的真实重复讲话拥有独立 occurrence ID，继续正常处理。

### 纯携带的 discourse 短前缀，在登记前组成后续单元

硬切携带的 `Yeah Well, first.`、`Yeah Well, first of all.` 等短引导语，可能被标点误判为独立完整句，又无法在下一窗口获得覆盖整段前缀的新解码证据。本次仅对明确属于携带范围、尚未登记的这类有限模式进行组装。

规则通过有效文本中的实际位置确认哪些完整单元全部位于 carry 内；匹配限定为 `yeah`、`well`、`so`、`okay` 的组合加 `first`、`first of all` 或 `secondly`，而非对所有短句使用通用长度阈值。若后续已有相邻的新完整单元，则把短前缀按原顺序拼入该单元，并继续应用既有语义依赖检查。后续内容尚未完整时，全部文字留在待处理尾部；不先登记一个无法确认的短队首，也不丢弃前缀。

已登记单元、真实新解码中的独立短句、不同的完整携带句和停止后的最终协调不套用此规则。新 raw 中真实重复的短语继续保留，不能因为它与 carry 的文字相同就删除。此项处理没有增加普遍的最终重解码，也不保证消除所有携带前缀的确认等待。

### 确认与验收保持严格

范围完整性只证明内容由哪一行接管，不能充当朗读确认票数。实时确认的词序、边界计票仍要求真实的新解码回调；拼接 carry、重复观察同一 chunk、播放器低缓冲或经过固定时长均不构成新证据。既有封口和停止排空路径保留，没有增加超时放行或频繁硬切措施。否定、数字、专名和语义依赖的既有保护不放宽。

回归覆盖完整多行合并、部分范围拒绝、已发布范围拒绝、真实重复讲话、迟到旧 MT、封口与结束排空、防止退休行复活，以及纯携带短前缀组装和尾部保留。修复后的运行验收仍需使用相同固定音频区间，对照确认等待、首次 PCM、原生积压、尾句排空与每个已接受 occurrence 的发布覆盖。

此次源范围保护不能推导全系统零遗漏；ASR 漏识、翻译语义误差、队列饱和与其他播放路径仍需独立检查。

实测覆盖与限制：

- 本轮有 118 次运行期首 PCM 发布，END 后没有额外首 PCM。117 次普通发布全部具有可匹配的 occurrence tuple，没有源 token 交集或同修订重复首 PCM。

- 最终没有真正待发布或未解释的最新修订，待播与预合成队列、活动任务及积压均清空，会话正常停止，采样和服务错误均为 0。原生停止路径会等待接收/播放游标排空，但本轮没有录制物理扬声器输出。
